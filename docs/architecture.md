# Architecture

The package owns one Harness LLM Service Provider. It uses the existing `ctx.llm` Service Definition and Harness Agent loop Consumer; it does not introduce another tool executor or keep authoritative conversation state outside the Harness session log.

Each ordinary conversation session may hold one bounded in-memory lease containing a private empty working directory, pinned Codex App Server `0.147.0` process, and ephemeral thread. The thread receives the selected model, Harness system text, Harness dynamic-tool declarations, no workspace roots or environment providers, a read-only sandbox, and `never` approval policy. The process explicitly enables native image viewing and, by default, the pinned image-generation capability required by the native `imagegen` skill while leaving unrelated native integrations disabled. Image generation is disabled for every compaction and search process and may be disabled for ordinary turns through the plugin settings snapshot. The process-level `model_auto_compact_token_limit` is set to Harness's safe integer ceiling so logged Harness compaction can replace history before Codex initiates opaque compaction. Calls without a Harness session id and auxiliary calls use a fresh one-shot thread. Code Mode remains available because `gpt-5.6-sol` uses that Codex layer to dispatch dynamic tools.

The provider is layered. `baseInstructions` and the `deepseek_harness` dynamic-tool namespace carry Harness inputs, while App Server adds Codex-owned instructions, context, and tools. The namespace is the ownership label: only callbacks bearing it can cross into the Harness tool loop. The Harness `skill` tool uses the additional App Server name `harness_skill`, and its input schema enumerates only the current Harness session catalog; Codex-native skills remain on Codex's loader. The adapter emits a lifecycle-category `thread/start` `codex-action` block containing the App Server identity and discovered instruction sources. This report describes provider setup, not a model action. The keyless outbound-wire test owns the more complete characterization of Codex-generated layers that App Server does not expose through `instructionSources`.

Provider-following auxiliary work remains outside the main thread. A Harness compaction request resolves the same provider/model as the initiating Agent, accepts the configured `maxTokens` only as an advisory budget, suppresses dynamic Harness tools, and uses the naturally completed Codex text as the durable summary. A `web_search` tool call is conditionally intercepted only when `exec.agent` resolves to this plugin's provider and the live settings snapshot enables takeover; each query runs an isolated App Server with `web_search="live"`, using the settings-owned search model override or otherwise the initiating model, and raw URL citations become the original tool definition's normalized value. Disabled takeover and non-Codex executions delegate through `next()` unchanged. This around-dispatch seam keeps the base Web provider installed and avoids concurrent turns on a main Codex thread that is waiting for the tool result.

The Harness session log and complete `GenerateOptions.messages` list remain authoritative. A cold lease injects all derived Responses items with `thread/inject_items` and starts an empty turn. An idle warm lease accepts the exact synchronized history plus one or more ordinary user messages: the first uses `turn/start.input`, and later messages use ordered `turn/steer` requests. A tool-waiting lease accepts its matching result followed by zero or more ordinary user messages, replies to the callback first, then steers those messages into the active turn. Any non-prefix history change or change to the model, reasoning effort, system text, tool catalog, provider route, App Server version, or fixed thread policy disposes the lease and reconstructs from the complete request. Replay snapshots are folded into one timeline by stable response item id or typed call id; the newest provider representation replaces an older provider representation, while a Harness-derived call or result remains authoritative over a provider echo. Items without a stable identity stay distinct. The mapper compares raw response items with that request baseline, treating absent and `null` optional fields as the same encoding. Repeated baseline items are ignored, Codex-added developer/system/user messages are displayed as context-category `context/injected` reports, and new provider outputs are retained for replay. Harness rc.8 carries replay state in `ReplayEnvelope.response`; the adapter accepts that envelope and the older direct carrier. Response state version `4` stores outputs in `items` and observed Codex context in `contextItems`; only `items` are reconstructible history. Harness tool calls map to namespaced `function_call` items with their App Server names, and results map to `function_call_output` items, with their original call ids.

Every model-visible Harness image is represented durably by a versioned attachment marker in the derived Responses history. Before any attachment read, the adapter computes projected base64 size from marker metadata and replaces the oldest provider-visible image occurrences until the request fits `maxRequestImageBytes`; provider trajectory markers are excluded. A cold lease hydrates retained markers into Responses `input_image` data URLs for `thread/inject_items`. An exact warm user continuation hydrates only its appended content into App Server v2 `text`/`image` input; an exact pending tool continuation hydrates only its result into callback `inputText`/`inputImage` items. The lease watermark always remains marker-based, so a changed offload prefix forces a cold rebuild instead of letting a live thread retain an omitted image. Codex-native image generation produces both a `ThreadItem` result and a raw `function_call_output` image. Before either value reaches a Harness stream chunk, the adapter decodes, validates, and commits it through `ctx.attachments`, emits one standard Harness image block, and replaces binary fields with the same marker. Supplied-image echoes are externalized without being republished; new generated outputs publish once. The adapter never persists a data URL or infers a workspace destination.

The JSON-RPC transport bounds each newline-delimited message and retained stderr, correlates client requests, accepts notifications and server requests concurrently, and rejects malformed JSON or unknown response ids. Successfully parsed messages do not accumulate against a whole-turn stdout limit, so valid long-running streams remain bounded by their pending frame instead of their duration. Reasoning and assistant deltas become open Harness blocks immediately. Raw completion events provide replay items and disjoint token usage. Codex `cachedInputTokens` becomes Harness `cacheReadTokens`; the shared token meter computes cache-hit percentage from cached and uncached input. A terminal step closes open blocks, emits any usage observed so far, and then emits exactly one finish chunk.

An App Server `item/tool/call` in the `deepseek_harness` namespace for a declared mapped name is the Harness tool handoff. The adapter validates the namespace, mapped name, and object-valued arguments before restoring the Harness name. `harness_skill` also validates its requested name against the latest logged Harness session catalog. The adapter then emits one Harness `tool-call`, ends the step with `tool-calls`, and leaves that JSON-RPC request pending. A raw call item is suppressed from Codex action reports only when the same namespace and mapped name identify Harness ownership, so one request has one owner and one presentation. Harness executes and logs the tool; the next append-only session request replies to the pending callback, steers following inbox messages, and continues the same Codex turn. Replacement or reordered history forces a cold reconstruction instead of merging into a live callback.

All other Codex action lifecycles remain provider trajectory. App Server `ThreadItem` start, progress, approval, and completion events become atomic action-category `codex-action` blocks. Novel non-message raw Responses items also become action reports, which preserves completed Code Mode `custom_tool_call` and `custom_tool_call_output` pairs that have no `ThreadItem` pair. A custom call or output without its mate remains visible in the current trajectory but is omitted from reconstructible replay because a fresh Code Mode host cannot resume it; the canonical Harness function call and result preserve a suspended Harness handoff. Codex-native skill reads remain visible as provider trajectory and cannot enter the Harness skill registry without the namespace, `harness_skill` alias, and catalog match. Every report contains its semantic category, parsed phase, exact protocol event, and a JSON snapshot; native image byte fields use the durable attachment marker described above. A native action can settle as `failed` or `declined` while the Harness request still succeeds; only an actual failed turn becomes a model-request failure. Approval, elicitation, and user-input server requests receive safe declines; current-time reads receive the current Unix time; unsupported requests receive a protocol error and are still reported.

The same package exposes a Web client entry. Harness's keyed slot priority lets this out-of-tree plugin shadow the built-in `assistant-step` renderer without redeclaring the slot or changing the Harness repository. The replacement preserves ordinary Assistant block behavior and recognizes only validated `codex-action` records. It uses Harness's compact disclosure row, neutral category icons, exceptional-status dots, and JSON tree to present the interpreted category, action, phase, protocol event, id, and complete record; every other custom block keeps the generic JSON fallback. A `requested` or `started` record is visibly ongoing only while its Assistant step is streaming and no terminal record with the same action id is present. An `updated` record is an observed atomic event and is settled immediately. Consecutive image blocks delegate to the rc.8 `conversation.message.images` render callback instead of importing attachment React atoms directly. The browser module therefore uses Harness's shared React, slot, and primitive identities while the separately composed attachment client plugin owns image presentation and lifecycle. It also registers a keyed `settings.plugin.item` card for the Host-owned `llm-codex-app-server` settings namespace. The settings scope provides durable revision-fenced writes and live snapshots; image-generation policy participates in the cached-thread epoch, while search policy is captured independently for each one-shot tool execution.

Timeout, caller cancellation, protocol failure, malformed continuation, and consumer early-return discard the affected lease. Successful completion keeps it until session disposal, plugin unload, configurable idle expiry, or configurable least-recently-used capacity eviction. Every disposal detaches connection listeners, closes stdin, terminates and awaits the complete process tree with a bound, and removes the validated temporary directory. Cleanup failures are contained for asynchronous lifecycle eviction and combined with an active request failure without replacing its classification.

Harness compaction replaces the durable surface with a summary, so the next fully assembled request cannot match the old lease watermark and cold-reconstructs from that summary. The summary may be generated by the same Codex route in a one-shot process, but it is still ordinary completed text owned by the Harness checkpoint transaction. Native `compaction`, `compaction_trigger`, and `context_compaction` response items remain trajectory rather than replay; a native item or `thread/compacted` notification lets the current step settle but disposes its lease before another request. This defensive path prevents opaque encrypted provider state from becoming a Harness checkpoint even if the fixed threshold is ignored.
