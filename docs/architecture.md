# Architecture

The package owns one Harness LLM Service Provider. It uses the existing `ctx.llm` Service Definition and Harness Agent loop Consumer; it does not introduce another tool executor or keep authoritative conversation state outside the Harness session log.

Each call creates a private empty working directory, starts pinned Codex App Server `0.147.0` through `ctx.subprocess`, validates the initialization version, and creates an ephemeral thread. The thread receives the selected model, Harness system text, Harness dynamic-tool declarations, no workspace roots or environment providers, a read-only sandbox, and `never` approval policy. Code Mode remains available because `gpt-5.6-sol` uses that Codex layer to dispatch dynamic tools.

The provider is layered. `baseInstructions` and `dynamicTools` carry Harness inputs, while App Server adds Codex-owned instructions, context, and tools. The adapter emits a `thread/start` `codex-action` block containing the App Server identity and discovered instruction sources. The keyless outbound-wire test owns the more complete characterization of Codex-generated layers that App Server does not expose through `instructionSources`.

Before starting a turn, the adapter derives Responses items from the complete ordered `GenerateOptions.messages` list and appends them with `thread/inject_items`. The current user message is already in that logged list, so `turn/start` uses empty input. Successful assistant output stores raw Responses items in adapter replay state; later calls prefer that lossless state over reconstructed assistant text. Harness tool calls and results map to `function_call` and `function_call_output` items with their original call ids.

The JSON-RPC transport bounds total stdout and retained stderr, correlates client requests, accepts notifications and server requests concurrently, and rejects malformed JSON or unknown response ids. Reasoning and assistant deltas become open Harness blocks immediately. Raw completion events provide replay items and disjoint token usage. A terminal turn closes open blocks, emits usage, and then emits exactly one finish chunk.

An App Server `item/tool/call` for a declared dynamic tool is the Harness tool handoff. The adapter validates the name and object-valued arguments, emits one Harness `tool-call`, ends the step with `tool-calls`, and closes the process without responding to App Server. Harness executes and logs the tool; the next stateless call injects its result.

All other Codex action lifecycles remain provider trajectory. Item start, progress, approval, diagnostic, and completion events become atomic `codex-action` blocks with the original action type, lifecycle phase, and JSON snapshot. They never create Harness `tool/call` or `tool/result` events, and their presence is not a model-request failure. Approval, elicitation, and user-input server requests receive safe declines; current-time reads receive the current Unix time; unsupported requests receive a protocol error and are still reported.

Timeout, caller cancellation, protocol failure, tool handoff, successful completion, and consumer early-return all converge on the same teardown path. The connection listeners are detached, stdin is closed, the complete process tree is terminated and awaited with a bound, and the validated temporary directory is removed. Cleanup failures are combined with the primary failure without replacing its classification.
