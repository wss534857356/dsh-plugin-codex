# Architecture

The package owns one Harness LLM Service Provider. It uses the existing `ctx.llm` Service Definition and Harness Agent loop Consumer; it does not introduce another tool executor or keep authoritative conversation state outside the Harness session log.

Each call creates a private empty working directory, starts pinned Codex App Server `0.147.0` through `ctx.subprocess`, validates the initialization version, and creates an ephemeral thread. The thread receives the selected model, Harness system text, Harness dynamic-tool declarations, no workspace roots or environment providers, a read-only sandbox, and `never` approval policy. Code Mode remains available because `gpt-5.6-sol` uses that Codex layer to dispatch dynamic tools.

The provider is layered. `baseInstructions` and `dynamicTools` carry Harness inputs, while App Server adds Codex-owned instructions, context, and tools. The adapter emits a lifecycle-category `thread/start` `codex-action` block containing the App Server identity and discovered instruction sources. This report describes provider setup, not a model action. The keyless outbound-wire test owns the more complete characterization of Codex-generated layers that App Server does not expose through `instructionSources`.

Before starting a turn, the adapter derives Responses items from the complete ordered `GenerateOptions.messages` list and appends them with `thread/inject_items`. The current user message is already in that logged list, so `turn/start` uses empty input. The mapper compares raw response items with that injected baseline. Repeated baseline items are ignored, Codex-added developer/system/user messages are displayed as context-category `context/injected` reports, and new provider outputs are retained for replay. Replay state version `1` stores outputs in `items` and observed Codex context in `contextItems`; only `items` are reinjected. Harness tool calls and results map to `function_call` and `function_call_output` items with their original call ids.

The JSON-RPC transport bounds total stdout and retained stderr, correlates client requests, accepts notifications and server requests concurrently, and rejects malformed JSON or unknown response ids. Reasoning and assistant deltas become open Harness blocks immediately. Raw completion events provide replay items and disjoint token usage. A terminal turn closes open blocks, emits usage, and then emits exactly one finish chunk.

An App Server `item/tool/call` for a declared dynamic tool is the Harness tool handoff. The adapter validates the name and object-valued arguments, emits one Harness `tool-call`, ends the step with `tool-calls`, and closes the process without responding to App Server. A raw call item naming a declared Harness tool is retained for lossless replay but suppressed from Codex action reports, so one request has one owner and one presentation. Harness executes and logs the tool; the next stateless call injects its result.

All other Codex action lifecycles remain provider trajectory. App Server `ThreadItem` start, progress, approval, and completion events become atomic action-category `codex-action` blocks. Novel non-message raw Responses items also become action reports, which preserves Code Mode `custom_tool_call` and `custom_tool_call_output` events that have no `ThreadItem` pair. Every report contains its semantic category, parsed phase, exact protocol event, and lossless JSON snapshot. A native action can settle as `failed` or `declined` while the Harness request still succeeds; only an actual failed turn becomes a model-request failure. Approval, elicitation, and user-input server requests receive safe declines; current-time reads receive the current Unix time; unsupported requests receive a protocol error and are still reported.

The same package exposes a Web client entry. Harness's keyed slot priority lets this out-of-tree plugin shadow the built-in `assistant-step` renderer without redeclaring the slot or changing the Harness repository. The replacement preserves ordinary Assistant block behavior and recognizes only validated `codex-action` records. It presents their interpreted category, action, phase, protocol event, and id before a collapsible complete record; every other custom block keeps the generic JSON fallback. The browser module uses Harness's shared React, slot, primitive, and attachment modules, so it does not create duplicate framework instances.

Timeout, caller cancellation, protocol failure, tool handoff, successful completion, and consumer early-return all converge on the same teardown path. The connection listeners are detached, stdin is closed, the complete process tree is terminated and awaited with a bound, and the validated temporary directory is removed. Cleanup failures are combined with the primary failure without replacing its classification.
